# Project Proposal: Curved-Path Puzzle Solver via Learned-Heuristic-Guided Motion Planning

**Track:** Option 1 — Modern Deep Learning Pipeline (Training + Deployment)

**GitHub repository:** https://github.com/AaronChandler976/curved-path-puzzle-solver

## Problem Formulation

**Domain problem.** The core algorithmic problem here — decide which item to try moving next, when checking whether a move is even possible requires an expensive verification step, and when some of those moves must be curved or rotational rather than straight-line — recurs directly in industrial disassembly: multi-robot electric-vehicle battery teardown, cluttered-scene object retrieval, and recycling/maintenance disassembly all share this same structure (expensive per-attempt verification, occasional non-axis-aligned motion requirement), as reflected in recent applied work on hybrid task-and-motion planning for battery disassembly and RL-guided disassembly-sequencing decisions (literature survey, items 5 and 6). Interlocking puzzles are used here as a controlled, cheaply reproducible testbed for that same problem class — not because puzzle-solving is the target application, but because it isolates the core algorithmic question (order items to minimize expensive verification calls, some of which require curved motion) without needing real industrial hardware or proprietary data. Concretely: interlocking and cast-metal puzzles are today solved by manual trial and error, or, for the narrow case of axis-aligned "burr" puzzles, by classical combinatorial tools (e.g. BurrTools) that cannot represent rotational or curved extraction moves at all. We address: given a 3D model of an assembled interlocking puzzle (arbitrary piece shapes, arbitrary contact geometry), find a valid disassembly sequence, where each individual extraction move may require curved, non-axis-aligned rigid-body motion, using as few expensive geometric search operations as possible.

**Input/output specification.**
- *Input:* mesh geometry for each puzzle piece (from CAD or 3D scan) in its assembled pose.
- *Output:* an ordered sequence of piece extractions, each paired with a concrete, collision-free 6-DOF motion path (translation and/or rotation) that removes it, given the remaining pieces held static.

**Success criteria / target metrics.** (1) Solve rate: fraction of held-out puzzles fully disassembled within a fixed budget. (2) Query efficiency: number of calls to the underlying motion-planning oracle needed to find a full disassembly, compared to an uninformed search baseline using the same oracle — this is the primary metric, since it directly measures the value the learned component adds. (3) Wall-clock time to solution. (4) Generalization gap between models trained only on synthetic puzzles and models fine-tuned on a small set of real, physically-modeled puzzles. Metrics are reported separately for translation-only vs. rotation/curved-motion-required puzzles, to directly evidence that the system handles genuine nonlinear motion, not an approximation of it.

## Proposed Technical Approach

**High-level architecture.** A two-layer system. (1) A discrete high-level search decides which piece to attempt extracting next, given the current assembly state (which pieces remain, and their contact relationships). This search is guided by a trained neural network that estimates how much work remains from a given state, analogous to DeepCubeA's learned heuristic for Rubik's Cube. (2) Each candidate extraction is checked by a continuous, curved-path motion-planning oracle — Critical-Manifold-Guided RRT (CMG-RRT), from the 2026 open-source "Manifold-Guided Motion Planning for Tight Assemblies" — which either returns a real collision-free path (rotation included) or reports failure. Decomposing the problem this way keeps the expensive, high-dimensional part of motion planning (searching one piece's continuous 6-DOF pose space against static obstacles) tractable, while leaving the combinatorial "which piece, in what order" decision to the learned component.

**Chosen models and required interventions.** Two heuristic architectures are trained and compared, satisfying the two required Option 1 interventions: (1) *Architectural change* — a graph neural network (nodes = pieces, with pose and shape features; edges = current contact) versus a flat MLP over concatenated piece poses (the DeepCubeA-style baseline representation), evaluated for generalization across puzzles of different piece counts and shapes. (2) *Efficiency improvement* — the learned heuristic's explicit objective is minimizing motion-planning oracle calls versus an uninformed ordering search, which matters because each oracle call is computationally expensive, unlike a simple table lookup.

**Training procedure and realistic scale.** Both heuristic networks are trained from scratch via DeepCubeA-style approximate value iteration — not supervised learning on precomputed correct disassembly sequences, which would require already solving every training puzzle. Instead, random backward rollouts from the goal (fully disassembled) state generate scrambled training states, and each state's training target is estimated from the network's own current predictions for its neighboring states (a Bellman-style bootstrapped backup), not a ground-truth label. This is closer to self-play / TD-learning than to classification: every generated state contributes training signal, whether or not it lies on an efficient solution path. The one place this departs from DeepCubeA's original recipe is cost: on a Rubik's Cube, applying a candidate move is essentially free, but here, checking whether a candidate extraction is even legal requires a real motion-planning query, so unrestricted approximate value iteration would be bottlenecked by oracle cost before it reached meaningful scale. Training is therefore split into two phases to keep the required scale realistic on laptop/modest-cloud compute: Phase A runs the bulk of approximate value iteration — on the order of 10^4-10^5 sampled states, enough for the GNN-vs-MLP comparison to show a real, statistically meaningful learning curve — against the cheap discretized-action oracle (PyBullet collision checks, effectively free per query). Phase B transfers and fine-tunes the resulting heuristic against the real CMG-RRT oracle on a much smaller, deliberately curated set of curved/rotation-required cases (on the order of 10^2-10^3 queries, budget confirmed empirically in weeks 1-2 once per-query time is measured), which is also where final evaluation happens. This keeps the expensive oracle's role bounded to where it matters most — proving the curved-motion claim on real cases — rather than gating the entire training loop on it.

**Data sources.** Procedurally generated synthetic puzzle families of varying piece count and contact structure, with a training subset deliberately constructed to require rotational/curved extraction (e.g., keyed contacts that clear only at a specific angle) so the model is not merely translation-solvable. A small held-out set (5-15 puzzles) of real puzzles, CAD-modeled from physical measurements or 3D-scanned, used to evaluate synthetic-to-real generalization.

**Baselines.** DeepCubeA-style MLP heuristic; uninformed/greedy ordering search using the same CMG-RRT oracle; a cheaper discretized-action ablation (translate/rotate in fixed increments, physics-checked via PyBullet, following "Assemble Them All") to quantify what true curved-path planning gains over a discretized approximation.

**Evaluation-first plan.** Every claim is backed by a working demo (an animated, CMG-RRT-derived disassembly of a real puzzle requiring curved extraction) and quantitative metrics (oracle-call counts, solve rates, wall-clock time), logged across training runs, consistent with the course's evaluation-first requirement.
